1. 一个 Agent 请求在服务端的完整路径

上篇从程序（harness）的角度讲了工具循环。这一节换到服务端，看一次请求在机房里经过了哪些环节。以下综合 DeepSeek 公开的部署方案和 2026 年的 Agent 推理系统论文；闭源厂商的实际实现未公开，但公开论文里的架构大体一致。

① 请求到达 → 路由器：尽量把同一个对话分给"手里有它旧缓存"的机器
② 读旧 KV 缓存：从显存 / 内存 / 分布式存储里把前几轮的 K、V 取出来
③ prefill 机器：只计算这一轮新增的 token（工具结果、用户新消息）
④ 把完整 KV 缓存经高速网络传给 decode 机器
⑤ decode 机器：和成百上千个别人的请求拼成一批，逐 token 生成
      └─ 每步：可能用投机解码一次出 2 个 token；采样前用语法掩码保证工具调用 JSON 合法
⑥ 生成到"工具调用结束"标记 → 停止 → 返回给你的程序
⑦ 这一轮的 KV 缓存写回存储，等你下一轮请求来时复用
⑧ 你的程序执行工具（这段时间服务端不为你计算）→ 回到 ①

其中第 ③、④ 步把"读入"和"生成"放在不同机器上，正式名字叫 PD 分离（prefill-decode disaggregation）。第 ② 步和第 ⑦ 步是 Agent 特有的负担，下面第 3.3 节会讲到，这里在 2026 年已经变成了主要瓶颈之一。

2. 单卡视角：一张 80GB 显卡能同时服务几个 Agent

本站 LLaMA-3 8B 那篇算过"已有 8K 缓存后再生成 1 个 token 约 19.3 GFLOPs"。这是一个请求的账。服务商关心的是一张卡同时跑多少个请求，Agent 场景下的答案和直觉很不一样。

2.1 算法（沿用 LLaMA-3 8B 那篇的参数）

  • 权重：8.03B 参数 × 2 字节 = 16.06 GB
  • 每 token 的 KV 缓存：LLaMA-3 8B 那篇算过是 128 KiB = 131,072 字节
  • 一张 80GB 卡扣掉权重后剩约 63.9 GB（忽略激活和框架开销，所以这是上限）
  • 能放下的 token 总数：63.9 GB ÷ 131,072 字节 ≈ 48.8 万个 token

如果每个 Agent 对话已经累积到 65,000 token（上篇 30 轮算例的终点）：

48.8 万 ÷ 6.5 万 ≈ 7 个 Agent 对话。

2.2 这 7 个对话一起 decode，每一步要从显存搬多少数据

一批里每个请求生成 1 个 token，需要：

  • 把全部权重读一遍：16.06 GB（7 个请求共享这一次读取）
  • 把每个请求自己的 KV 缓存读一遍：7 × 65,000 × 131,072 字节 ≈ 59.6 GB

合计约 75.7 GB/步，其中 KV 缓存占 79%。

按 H100 SXM 规格表上的显存带宽 3.35 TB/s 算（理想化，假设带宽全部跑满）：每步约 22.6 毫秒，每个对话每秒约 44 个 token，整张卡每秒约 310 个 token。

2.3 这说明了什么

LLaMA-3 8B 那篇说 decode 受显存带宽限制，这是对的，但隐含的画面是"主要在读权重"。在 Agent 场景里，上下文很长，主要在读的是 KV 缓存。这带来两个直接后果：

  1. 把很多请求拼成一批，只能摊薄权重的读取，摊不薄 KV 的读取（每个请求的 KV 是它自己的）。所以对长上下文 Agent，批处理带来的收益有限。
  2. 上篇讲的 GQA、MLA 压缩 KV，在这里直接决定了一张卡能服务几个 Agent、每个 Agent 有多快。这也是第 4 节那些新注意力结构出现的根本动机。

3. 大模型在几百张卡上怎么切：以 DeepSeek-V3 的公开部署为例

上篇讲了 MoE 的结构：每个 token 只用 256 个专家里的 8 个。这一节讲这个结构在真实机房里怎么跑，DeepSeek-V3 技术报告第 3.4 节公开了数字。

3.1 一个 token 在 decode 集群里走一遍

大白话版：每张卡只放一个专家。一个 token 在自己所在的卡上算完注意力后，打分器选出它要用的 8 个专家，然后把这个 token 的向量通过网络发到那 8 张卡上，各自算完再收回来、按权重加起来，送进下一层。下一层再来一遍。

正式名字：把专家分散在不同卡上叫 expert parallelism（专家并行）；"发出去、收回来"这一对通信叫 dispatch / combine，底层是一种所有卡互相收发的通信，叫 all-to-all。

DeepSeek-V3 公开的部署规模：

阶段最小部署单元注意力部分MoE 部分
prefill（读入）4 台机器，32 张 GPU4 路张量并行 × 8 路数据并行32 路专家并行；每卡 8 个专家 + 1 个冗余专家
decode（生成）40 台机器，320 张 GPU4 路张量并行 × 80 路数据并行320 路专家并行；每卡 1 个专家，另有 64 张卡放冗余专家和共享专家

几个细节：

  • 每个 token 最多只发往 4 台机器（论文 4.2 节，节点上限 M = 4），用来限制跨机器的网络流量。
  • 冗余专家：有些专家特别热门，被选得多，所在的卡就会排队。解决办法是把热门专家多复制几份放到别的卡上分流。
  • 两批交错：把一批请求切成两个小批，一个小批在算注意力和专家时，另一个小批在做网络收发，让计算和通信互相掩盖。

3.2 为什么 decode 要用 320 张卡，而 prefill 只要 32 张

回到第 2 节的结论：decode 每一步每个请求只有 1 个 token，计算量很小，瓶颈在搬数据。卡分得越多，每张卡上的专家越少，每个专家一次能收到更多 token（来自整个集群的几百上千个请求），矩阵乘法才"吃得饱"。prefill 本身就有成千上万个 token，不需要这样拆。

3.3 Agent 带来的新瓶颈：存取 KV 缓存的网络带宽

DeepSeek 和北大、清华在 2026 年 2 月的论文（DualPath）专门分析了 Agent 负载。核心观察：

  • Agent 是"多轮、每轮只追加一小段"的模式，所以 KV 缓存命中率通常 ≥95%。上篇 30 轮算例算出来的 95% 和这个实测量级吻合。
  • 命中率高意味着 prefill 机器几乎不用算，但它必须先从外部存储里读回海量的旧 KV 缓存。结果是 prefill 机器的存储网卡被打满，decode 机器的网卡却闲着，整个系统被存储读取卡住，而不是被计算卡住。
  • 他们的解决办法是让 decode 机器也去读存储，再通过机器间的高速网络转给 prefill 机器，离线吞吐提高到最多 1.87 倍。

所以对 Agent 来说，GPT-3 那篇第五节那条"FLOPs → 电能"的链条只覆盖了一部分开销。前沿 Agent 推理的成本里，越来越大的一块是数据搬运：显存里搬 KV（第 2 节）、机器之间传 KV、存储读写 KV。

4. 长上下文注意力的两条新路线

4.1 先算一笔账：长上下文下注意力有多贵

上篇用 GPT-3 维度推过：注意力计算量在上下文达到 6d（73,728 token）时追上线性层。换成 DeepSeek-V3 这种 MoE 模型，情况更极端，因为 MoE 把线性层的计算量压得很小（每 token 只有 2 × 37B = 740 亿次），注意力却没有变小。

DeepSeek-V3 每生成 1 个 token，注意力部分的计算量（按每个头 Q·K 用 192 维、α·V 用 128 维的标准视角）：

每层每个上下文 token：2 × 128 头 × (192 + 128) = 81,920 次 61 层合计：约 500 万次 × 上下文长度 L

上下文长度 L注意力（每 token）线性层 + 专家（每 token）注意力 ÷ 线性
8,192约 410 亿约 740 亿0.55
14,800约 740 亿约 740 亿1（交叉点）
131,072（128K）约 6,550 亿约 740 亿8.9

[补充说明] MLA 在 decode 时常用一种"吸收"写法，直接在 512 维压缩空间里算注意力，省显存但计算量更大，按这种写法交叉点会提前到约 4,400 token。不同推理引擎的实现不同，上表取的是较乐观的口径。

结论：对 MoE 模型来说，Agent 动辄几万到十几万 token 的上下文里，注意力是每个 token 的主要计算开销，FFN 已经不是了。这正好把 GPT-3 那篇"FFN 贡献主要计算量"的结论翻转了过来。

4.2 路线一：稀疏注意力——只看最相关的 2,048 个 token（DeepSeek-V3.2）

大白话版：与其让每个新 token 都和前面 13 万个 token 逐一做完整的注意力，不如先用一个很便宜的小打分器把 13 万个 token 粗筛一遍，挑出最相关的 2,048 个，只和这 2,048 个做完整的注意力。

正式名字叫 DSA（DeepSeek Sparse Attention），由两部分组成：

  • lightning indexer（闪电索引器）：一个小型注意力，只有 64 个头、每头 128 维（公开配置 index_n_heads: 64、index_head_dim: 128），用 ReLU 代替 softmax，用 8 位浮点（FP8）计算。它给每个历史 token 打一个"相关度分数"。
  • top-k 选择：按分数取前 2,048 个（配置 index_topk: 2048），主注意力只在这些 token 上算。

DeepSeek-V3.2 相对上一版唯一的架构改动就是加了 DSA，靠继续训练接上去。

账怎么变（128K 上下文，每生成 1 个 token，61 层合计）：

部分计算结果
原来的主注意力500 万 × 131,072约 6,550 亿次（16 位）
稀疏后的主注意力500 万 × 2,048约 102 亿次（16 位）
索引器2 × 64 × 128 × 131,072 × 61约 1,310 亿次（8 位）

需要说清楚的一点：索引器仍然要扫一遍全部历史 token，所以每个 token 的计算量仍然随上下文长度线性增长，理论复杂度并没有消失。它的作用是把这笔"必须看全部"的开销，从 128 个头的 16 位完整注意力，挪到 64 个头的 8 位简化打分上。另外它还要多存一份自己用的 K 缓存，每 token 每层 128 维、8 位，61 层约 7.8 KB/token（不含缩放因子等附加量）。

公开评测：处理 7,000 token 以上的输入时速度提高到 2–3 倍，多数基准上的效果和上一版相当。

4.3 路线二：线性注意力混合——让大部分层的"记忆"大小固定（Qwen3-Next）

大白话版：普通注意力的"记忆"就是 KV 缓存，每多一个 token 就多存一份，上下文越长存得越多。另一种思路是给每个头一块固定大小的记事本（一个 d × d 的矩阵）：每读一个新 token，就用这个 token 的 k、v 去改写记事本；要查询时，用 q 去"读"记事本。不管读过 1 千还是 100 万个 token，记事本都一样大。

正式名字叫 linear attention（线性注意力），记事本叫 state（状态）。Qwen3-Next 用的是一种改进版，叫 Gated DeltaNet，它的更新规则是：

S_t = α_t · (I − β_t · k_t k_tᵀ) · S_{t−1} + β_t · k_t v_tᵀ，输出 o_t = S_tᵀ q_t

逐项用大白话读：

  • α_t（0 到 1 之间）：先把整本记事本淡化一点，相当于遗忘旧内容
  • (I − β_t k_t k_tᵀ)：把记事本里"和当前 k_t 方向有关"的旧内容擦掉一部分
  • β_t k_t v_tᵀ：在 k_t 这个"地址"上写入新的 v_t
  • β_t 控制擦写力度

"先擦再写"这一步来自一个老的学习规则（delta rule），作用是防止固定大小的记事本被反复叠加写成一团糊。

为什么不全用线性注意力：固定大小的记事本必然会丢信息，精确回忆远处某个细节的能力不如普通注意力。所以 Qwen3-Next 采取混合方案：48 层里 36 层用 Gated DeltaNet，12 层保留普通注意力（3:1）。阿里的实验结论是 3:1 混合的效果超过任何单一结构。

用公开配置算显存（Gated DeltaNet 层：32 个 V 头、每头 128 维；普通注意力层：2 个 KV 头、每头 256 维）：

36 层线性注意力的记事本（固定）36 × 32 × 128 × 128 × 2 字节37.7 MB，与上下文长度无关
12 层普通注意力的 KV（随长度增长）12 × 2 头 × 256 × 2（K 和 V）× 2 字节24 KiB/token

4.4 两条路线对照

稀疏注意力（DSA）线性注意力混合（Gated DeltaNet）
改的是什么少算：每次只和 2,048 个 token 做完整注意力少存：大部分层的记忆大小固定
KV 缓存不变（甚至多一份索引器缓存）只有 1/4 的层还有随长度增长的缓存
每 token 计算量随上下文仍线性增长，但大头挪到便宜的 FP8 索引器线性注意力层不随长度增长；普通注意力层仍增长

[补充说明] 闭源前沿模型采用了哪种（或都没有采用），官方均未公开。这里只说明 2025–2026 年公开模型里出现了这两条主流路线。

5. 让逐字生成变快：投机解码

5.1 原理

第 2 节说过，decode 时 GPU 大部分时间在等数据，计算单元很闲。投机解码的想法是利用这份闲置：

  1. 先用一个很便宜的办法猜接下来的几个 token（比如猜 1 个）。
  2. 把"当前 token + 猜的 token"一起送进大模型，做一次小规模的并行前向传播，相当于一个只有 2 个 token 的 prefill。因为是并行算，花的时间和只算 1 个 token 差不多，瓶颈仍是搬权重和 KV。
  3. 大模型这一次算出了两个位置各自的"真正的下一个词"分布。如果猜的那个 token 和大模型的结果一致（按一套保证输出分布不变的规则判定），就一步拿到 2 个 token；不一致，就丢掉猜的那个，至少还拿到 1 个正确的。

正式名字叫 speculative decoding（投机解码），猜 token 的部件叫 draft（草稿），大模型检查叫 verify（验证）。关键性质是：输出质量不变，只是变快。

5.2 DeepSeek-V3 的做法：模型自带一个"多猜一个"的小模块

DeepSeek-V3 训练时就额外加了一层轻量模块，学习预测"下下个 token"，正式名字叫 MTP（Multi-Token Prediction，多 token 预测）。推理时这个模块直接当草稿用。

公开数据：第二个 token 的接受率在 85%–90% 之间，生成速度（每秒 token 数）提高到 1.8 倍。

验算：每步期望拿到的 token 数 = 1 + 接受率 = 1.85～1.9。实测 1.8 倍略低于这个理论值，因为验证本身也有少量额外开销。

5.3 和 Agent 的关系

Agent 输出里有大量格式高度可预测的内容：工具调用的 JSON 框架、参数名、重复引用的文件路径和代码片段。这些地方草稿的命中率往往更高，投机解码对 Agent 特别有效。第 8 节会讲到，它甚至被用到了强化学习训练里。

6. 采样这一步多了什么：保证工具调用格式合法

LLaMA-3 8B 那篇第十节讲了采样：logits → softmax → argmax / top-k / top-p。Agent 在这一步多了一个环节。

6.1 问题

工具调用必须是合法的 JSON，并且要符合工具定义的参数格式。模型偶尔会写错（漏一个引号、参数名拼错、类型不对），程序就解析不了。

6.2 做法

大白话版：把"合法的 JSON 长什么样"写成一套语法规则，编译成一台状态机。每生成一个 token 前，先问状态机："在当前位置，词表里哪些 token 接上去之后还可能是合法的？"把所有不合法 token 的 logit 设成负无穷（softmax 后概率为 0），再正常采样。这样模型物理上无法写出不合法的格式。

正式名字叫 constrained decoding（受约束解码） 或 guided decoding，开源实现里常用的引擎是 XGrammar。

计算上的代价：每步要算一个和词表等长的掩码（LLaMA-3 是 128,256 个位置）。优化过的引擎会把大部分 token 的合法性预先算好缓存起来，只在运行时补算少量依赖上下文的部分，并且和 GPU 的前向计算重叠进行，所以对 JSON 这类语法的开销可以忽略。

只约束工具调用部分：Agent 的输出一般是"自由文本 + 工具调用"混在一起。推理引擎支持"遇到触发标记（比如工具调用开始的标记）之前不约束，进入调用之后才按参数格式约束"，叫 structural tag。

Claude API 对应的功能是在工具定义里加 strict: true（strict tool use），文档说明这样可以完全消除无效的工具调用。Anthropic 内部如何实现没有公开。

7. Agent 一次任务的总账：多 Agent 和工具定义

7.1 Anthropic 公开的倍数

Anthropic 在介绍其多 Agent 研究系统时公开了几组数字：

  • 单个 Agent 的 token 用量约是普通聊天的 4 倍；多 Agent 系统约是 15 倍。
  • 在他们的评测里，token 用量一项就解释了 80% 的效果差异。他们的总结是：多 Agent 系统之所以有效，主要是因为它帮你花够了解决问题所需的 token。
  • 结构是"主 Agent 规划 + 多个子 Agent 并行搜索"，每个子 Agent 有自己独立的上下文，最后只把浓缩后的结论交回主 Agent。以 Claude Opus 4 为主、Claude Sonnet 4 为子 Agent 的组合，在内部研究评测上比单个 Opus 4 高 90.2%。

从计算角度翻译一下：多 Agent 用更多的并行前向传播（多个上下文同时跑）换来了更大的有效上下文（每个子 Agent 都能读满自己的窗口），代价是总 token 数成倍增长。这和 GPT-3 那篇第五节"调用次数 × 单次能耗"的框架直接相关：Agent 化之后，"单次调用"的 token 数本身就放大了 4 到 15 倍。

7.2 工具定义本身就是一笔大开销

上篇的算例假设"系统提示 + 工具说明 2 万 token"。如果接了很多工具，这个数字会大得多：每个工具的名字、说明、参数格式都要写进上下文，每轮都要（从缓存）读一遍。

Anthropic 2025 年 11 月的工程文章给出了一个实例：一个"从 Google Drive 读文档、写入 Salesforce"的任务，常规做法要 15 万 token；改成"让模型写一段代码去调用工具、只把精简后的结果放回上下文"之后，降到 2,000 token，减少 98.7%。原理有两个：

  1. 工具说明不再一次性全部放进上下文，模型需要时再去"查阅"某个工具的定义。
  2. 工具之间传递的大块中间数据留在代码执行环境里，不再经过模型的上下文。

从计算角度看，这相当于把一部分原本由模型 prefill 和注意力承担的工作，挪给了普通的确定性程序。这和上篇第 6.3 节讨论的"Graph 用低成本、高确定性的规则兜底"思路方向一致，只是实现方式是"模型写代码"，而不是预先画好的图。

7.3 一次 Agent 任务的成本公式

把上篇和本篇合起来，一次 Agent 任务的服务端开销可以写成：

总开销 ≈ Σ（每个 Agent）Σ（每一轮）[
      新增 token 数 × prefill 单价            ← 计算密集
    + 旧上下文 token 数 × 缓存读取单价        ← 数据搬运（显存/网络/存储）
    + 生成 token 数 × decode 单价             ← 显存带宽受限，随上下文变长而变贵
]

各种技术分别在压哪一项：

技术压哪一项本系列出处
前缀缓存把"旧上下文"从 prefill 价降到缓存读取价上篇第 4 节
GQA / MLA / 线性注意力混合缓存读取和 decode 的数据量上篇 1.3；本篇 4.3
稀疏注意力长上下文下 decode 的计算量本篇 4.2
MoE每 token 的线性层计算量上篇 1.4
投机解码decode 的步数本篇第 5 节
压缩、子 Agent、按需加载工具、代码执行每一轮的上下文长度本身上篇 5.2；本篇第 7 节

8. 训练侧：Agent 强化学习的算力花在哪里

本站 GPT-3 和 LLaMA-3 那两篇用 6NT 估算预训练算力，那是"一次前向 + 一次反向，所有 token 并行"的账。Agent 强化学习的账完全不同。

8.1 一步强化学习里有什么

① 生成（rollout）：当前模型在沙盒里把每道题完整做一遍，可能几十轮工具调用
     ↑ 这一步本质上就是推理：大量 decode、KV 缓存、工具执行等待
② 打分：跑测试 / 比对答案，得到奖励
③ 训练：对生成出来的 token 序列做一次前向 + 反向，按 GRPO 等算法更新权重
④ 把新权重同步给负责生成的机器 → 回到 ①

8.2 时间几乎都花在生成上

多篇 2025–2026 年的系统论文给出了实测比例：

  • 生成阶段通常占总训练时间的 70% 以上；有工作报告最大回答长度 16K 时，数学模型占 91%、代码模型占 84%；也有工作给出的范围是 50%–80%。
  • 原因是长尾：同一批题目里，大部分回答很快结束，少数特别长的回答会拖住整批，其余 GPU 只能空等。有测量显示长尾阶段能占到生成时间的近一半。而且训练越往后，模型的回答往往越来越长。

对 Agent 任务，长尾更严重：除了生成长度不一，还要等工具执行、沙盒启动，单道题的轨迹可能有几十轮。

8.3 应对办法

  • 异步训练：生成和训练放在不同的机器上同时进行，不再互相等待。代价是训练用的数据可能来自"旧一两版的模型"，正式名字叫 off-policy，需要算法上做修正，否则收敛会受影响。所以也有很多团队仍然坚持同步训练。
  • 把长尾任务集中处理：把可能产生长回答的题目归到一起调度，或者把没做完的轨迹截断，留到下一轮接着做。
  • 在生成阶段用投机解码：第 5 节的技术被用来加速强化学习里的生成，甚至把长尾造成的空闲时间拿来生成草稿。
  • 沙盒服务化：每条轨迹一个独立沙盒，用完即毁；沙盒的创建和回收本身也成了需要专门优化的系统（例如 2026 年的 Sandman、ProRL Agent）。

8.4 这对 GPT-3 那篇第五节的"能耗链条"意味着什么

预训练的算力主要是大矩阵乘法（计算密集，利用率可以较高）。Agent 强化学习的算力大头却是生成，也就是 decode：显存带宽受限、长尾空等、工具等待。所以"总 FLOPs ÷ 每瓦 FLOP/s"这条换算在这里会更严重地低估实际能耗。GPT-3 那篇已经解释过实际吞吐只有峰值约 20% 的问题，在 Agent 强化学习里这个比例很可能更低。目前没有找到公开的、针对 Agent 强化学习的端到端能耗实测，这里只能给出定性判断。

9. 把三份材料合起来：一次前沿 Agent 任务的完整计算栈

从下往上：

层发生了什么主要瓶颈出处
1. 一层的计算归一化 → 注意力（GQA / MLA / 稀疏 / 线性）→ 残差 → FFN 或 MoE → 残差短上下文：FFN/MoE；长上下文：注意力本站 GPT-3、LLaMA-3；上篇 1；本篇 4
2. 一个 token穿过全部层（深度固定）；采样前加语法掩码；可能一次投机出 2 个decode 时的显存带宽本站 LLaMA-3；本篇 5、6
3. 一次模型调用prefill 新增部分 + 读旧 KV + decode 到停止标记KV 缓存的显存容量和读取带宽上篇 2；本篇 2
4. 多请求共用硬件连续批处理；PD 分离；专家并行与 all-to-all网络通信；专家负载均衡本篇 1、3
5. 跨轮复用前缀缓存；KV 缓存写回 / 读取分布式存储存储网络带宽（命中率 ≥95% 时）上篇 4；本篇 3.3
6. 一个 Agentwhile 循环：模型 ↔ 工具；上下文压缩、笔记每轮上下文长度；工具等待上篇 3、5
7. 多个 Agent主 Agent + 并行子 Agent，各自独立上下文总 token 数（约 15 倍于聊天）本篇 7
8. 训练沙盒里生成轨迹 → 可验证奖励 → GRPO 更新 → 同步权重生成阶段（占 70%+）、长尾上篇 7；本篇 8

和上篇第 8 节那张"GPT-3 一次前向传播 vs 现代 Agent 一次任务"对照表相比，最大的变化是：Agent 的"智能"仍然来自第 1、2 层那套固定深度的前向传播；第 3 到第 8 层几乎全是让这套前向传播能被更长、更多、更频繁地调用的工程体系。 2025–2026 年这几层的进展速度，并不比模型本身慢。

10. 不确定或没有公开的部分

  • Claude、GPT 等闭源模型：是否用稀疏注意力、线性注意力、MTP，用多少张卡怎么切分，strict 工具调用如何实现——均未公开。
  • 第 2 节单卡算例忽略了激活值、框架开销、显存碎片，带宽按规格表峰值计算，是理想化上限。
  • 第 4.1 节注意力计算量取的是标准视角，MLA 在不同推理引擎里的实际写法不同，计算量会有约 3 倍的差别（已在补充说明中给出另一口径）。
  • 第 4.2 节索引器的计算量按全精度乘加次数估算，没有计入 FP8 的实际速度优势和 top-k 选择本身的开销。
  • 第 8 节生成阶段的占比来自不同论文、不同任务和不同集群，范围较宽（50%–91%），不应当作一个统一的常数。
